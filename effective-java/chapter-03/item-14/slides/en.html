Where compareTo lives

Not in Object

equals

Declared in Object.
Answers: are they equal?

compareTo

Declared in Comparable.
Answers: which comes first?

Implementing Comparable declares that instances have a natural ordering.

compareTo is Comparable's only method. It resembles equals, but beyond equality it permits order comparisons, and it is generic: Comparable compares only with T. A natural ordering is the order that makes sense by default for the type: alphabetical, numerical, chronological. String, Integer, BigDecimal and the java.time types already implement it.
The test: Object does not declare compareTo
contract/NaturalOrderingTest.java
Reflection lists Object's public methods: equals is there, compareTo is not. The ability to be ordered comes from an optional interface the class chooses to implement.
Why implement it

One method,
many algorithms

Collections.sort · binarySearch · max · TreeSet · TreeMap

Everything that depends on Comparable works with no extra code.

Generic algorithms and sorted collections depend on this interface. With little effort a class gains sorting, searching, extremes and sorted collections. If a class is a value with an obvious natural ordering, implement Comparable. We use the book's CaseInsensitiveString: it compares ignoring case.

The general contract

Negative, zero or positive

Reflexivity · x.compareTo(x) == 0

Symmetry · sgn(x.compareTo(y)) == -sgn(y.compareTo(x))

Transitivity · x > y && y > z ⇒ x > z

If x.compareTo(y) == 0, x and y compare alike against any z.

Compares this object with the specified object for order: returns a negative integer, zero or a positive integer as this object is less than, equal to or greater than it. Only the sign matters, not the value. These are the same restrictions as equals: reflexivity, symmetry and transitivity. Symmetry covers exceptions too: x.compareTo(y) throws if and only if y.compareTo(x) throws. Strongly recommended, not required: (x.compareTo(y) == 0) == x.equals(y).

The test: transitivity

Every triple. The second condition is the least remembered clause: values that tie must behave alike against any third value.
Unlike equals

Different types?
It may throw

equals must answer false for another type.
compareTo may throw ClassCastException.
The equals contract applies to any Object. compareTo need not work across different types, and that is exactly what usually happens. With generics the compiler already prevents the call; through a raw type, the generated bridge method performs the cast and throws ClassCastException.
The test: false versus exception
contract/NaturalOrderingTest.java
equals with a String returns false. compareTo with the same String, through the raw reference, throws ClassCastException. No line in our compareTo deals with the type: the cast comes from the compiler.
Synergy

TreeSet uses compareTo,
not equals

Order

Elements come out sorted.
No call to sort.

Uniqueness

compareTo == 0 is a duplicate.
equals is not consulted.

TreeSet and TreeMap use compareTo to place elements and to decide duplicates. The Set and Map interfaces are defined in terms of equals. When compareTo and equals disagree, the collection still works but does not obey the interface's general contract. The book's example is BigDecimal: 1.0 and 1.00 differ under equals and are equal under compareTo.

The Item 10 rule

There is no way to extend
and add a value

Point → ColorPoint

You cannot extend an instantiable class with a new value component while preserving the compareTo contract, unless you give up the benefits of object-oriented abstraction.

It is the same limitation as equals. A Java detail: ColorPoint extends Point cannot even declare implements Comparable, because Comparable cannot be inherited with different arguments. The subclass is stuck with compareTo(Point). We look at two attempts and the way out.
Attempt A: compare color only with ColorPoint
inheritance/Point.java
inheritance/ColorPointBrokenTransitivity.java
Point orders by x and y. The subclass adds color as a tiebreaker only when the other side has a color too; against a plain Point, it compares position only.
The test: transitivity breaks
inheritance/ColorPointBrokenTransitivityTest.java
Red ties with the plain point, which ties with blue, but red and blue differ. Practical consequence: the same three points produce a TreeSet of two or of one element, depending only on insertion order.
Attempt B: getClass()

Breaks the Liskov
substitution principle

A ColorPoint stops working
wherever a Point is expected.

Throwing ClassCastException is allowed; throwing on one side only is not.

Same as the Item 10 getClass attempt. ColorPoint rejects anything that is not exactly its class. The contract allows the exception for different types, but Point still accepts the ColorPoint. p.compareTo(cp) answers and cp.compareTo(p) throws: exception symmetry is violated. By the Liskov principle, any important property of a type holds for its subtypes; here a method written for List fails when handed a subtype.
Reject anything not of the same class
inheritance/ColorPointGetClass.java
Within its own class the order is correct: position, then color. The trouble is at the boundary with the superclass.
The test: the same list works or blows up
inheritance/ColorPointGetClassTest.java
Collections.max is written for List. With the ColorPoint first, the Point does the comparing and everything works. With the Point first, the ColorPoint does the comparing and the exception appears. Behavior depends on element order, not on values.
The way out

Composition
instead of inheritance

Has a Point

Not a subtype.
Defines its own order.

View

asPoint() returns the Point
for whoever needs it.

Same advice the book gives for equals: write an unrelated class holding a field of the original type plus a view method. With no subtype relationship, there is no superclass contract to defend.

Multiple fields

From the most
significant field down

areaCode → prefix → lineNum

Use Integer.compare, never < and > or subtraction.

Compare the most significant field first. If the result is nonzero it decides; otherwise move to the next field. Since Java 7, the wrapper classes' static compare methods replace the relational operators, which the book calls verbose and error-prone.

A real case

Subtraction overflows

return this.priority() - other.priority();

open-workflow-specification/sdk-java #1799

The book shows a hashCode-difference comparator as what not to do: subtraction overflows int and violates transitivity. In the Open Workflow Java SDK, ServicePriority did exactly that, and it decides which implementation ServiceLoader picks at almost every extension point. An implementation returning Integer.MIN_VALUE to always win would lose, with no exception at all. Issue 1797; fixed in PR 1799.
