Onde vive compareTo

Não está em Object

equals

Declarado em Object.
Responde: são iguais?

compareTo

Declarado em Comparable.
Responde: quem vem antes?

Implementar Comparable declara que as instâncias têm uma ordenação natural.

compareTo é o único método de Comparable. É parecido com equals, mas além de igualdade admite comparações de ordem, e é genérico: Comparable compara apenas com T. Ordenação natural é a ordem que faz sentido por padrão para o tipo: alfabética, numérica, cronológica. String, Integer, BigDecimal e os tipos de java.time já a implementam.

Por que implementar

Um método,
muitos algoritmos

Collections.sort · binarySearch · max · TreeSet · TreeMap

Tudo que depende de Comparable passa a funcionar sem código extra.

Algoritmos genéricos e coleções ordenadas dependem dessa interface. Com pouco esforço a classe ganha ordenação, busca, extremos e coleções ordenadas. Se a classe é um valor com ordem natural óbvia, implemente Comparable. Usamos o CaseInsensitiveString do livro: compara ignorando maiúsculas e minúsculas.

O contrato geral

Negativo, zero ou positivo

Reflexividade · x.compareTo(x) == 0

Simetria · sgn(x.compareTo(y)) == -sgn(y.compareTo(x))

Transitividade · x > y && y > z ⇒ x > z

Se x.compareTo(y) == 0, x e y se comparam igual com qualquer z.

Compara este objeto com o especificado para determinar a ordem: retorna um inteiro negativo, zero ou positivo se este objeto for menor, igual ou maior. Só o sinal importa, não o valor. São as mesmas restrições do equals: reflexividade, simetria e transitividade. A simetria inclui exceções: x.compareTo(y) lança se e somente se y.compareTo(x) lança. Recomendação forte, mas não obrigatória: (x.compareTo(y) == 0) == x.equals(y).

Diferente do equals

Tipos diferentes?
Pode lançar exceção

equals deve responder false para outro tipo.
compareTo pode lançar ClassCastException.
O contrato de equals vale para qualquer Object. compareTo não precisa funcionar entre tipos diferentes, e é exatamente isso que costuma acontecer. Com genéricos o compilador já impede a chamada; via tipo raw, o método bridge gerado faz o cast e lança ClassCastException.
O teste: false contra exceção
contract/NaturalOrderingTest.java
equals com uma String retorna false. compareTo com a mesma String, pela referência raw, lança ClassCastException. Nenhuma linha no nosso compareTo trata o tipo: o cast vem do compilador.
Sinergia

TreeSet usa compareTo,
não equals

Ordem

Os elementos já saem ordenados.
Nenhuma chamada a sort.

Unicidade

compareTo == 0 é duplicata.
equals não é consultado.

TreeSet e TreeMap usam compareTo para posicionar e para decidir duplicatas. As interfaces Set e Map são definidas em termos de equals. Se compareTo e equals discordam, a coleção ainda funciona, mas não obedece ao contrato geral da interface. O exemplo do livro é BigDecimal: 1.0 e 1.00 são diferentes para equals e iguais para compareTo.

A regra do Item 10

Não há como estender
e adicionar valor

Point → ColorPoint

Não dá para estender uma classe instanciável com um novo componente de valor preservando o contrato do compareTo, a menos que se abra mão da abstração orientada a objetos.

É a mesma limitação do equals. Detalhe de Java: ColorPoint extends Point nem pode declarar implements Comparable, porque Comparable não pode ser herdado com argumentos diferentes. A subclasse fica presa a compareTo(Point). Vamos ver duas tentativas e a saída.
Tentativa A: comparar cor só com ColorPoint
inheritance/Point.java
inheritance/ColorPointBrokenTransitivity.java
Point ordena por x e y. A subclasse acrescenta a cor como desempate apenas quando o outro lado também tem cor; contra um Point puro, compara só a posição.
O teste: a transitividade quebra
inheritance/ColorPointBrokenTransitivityTest.java
Vermelho empata com o ponto sem cor, que empata com o azul, mas vermelho e azul são diferentes. Consequência prática: os mesmos três pontos geram um TreeSet com dois ou com um elemento, dependendo só da ordem de inserção.
Tentativa B: getClass()

Quebra o princípio
de Liskov

Um ColorPoint deixa de funcionar
onde um Point é esperado.

Lançar ClassCastException é permitido; lançar só de um lado, não.

Igual ao getClass do Item 10. ColorPoint recusa qualquer objeto que não seja exatamente da sua classe. O contrato permite a exceção para tipos diferentes, mas Point continua aceitando o ColorPoint. p.compareTo(cp) responde e cp.compareTo(p) lança: a simetria de exceções é violada. Pelo princípio de Liskov, qualquer propriedade importante de um tipo vale para seus subtipos; aqui, um método escrito para List falha quando recebe um subtipo.
Recusar tudo que não for a mesma classe
inheritance/ColorPointGetClass.java
Dentro da própria classe a ordem é correta: posição e depois cor. O problema está na fronteira com a superclasse.
O teste: a mesma lista funciona ou explode
inheritance/ColorPointGetClassTest.java
Collections.max foi escrito para List. Com o ColorPoint primeiro, quem compara é o Point e tudo funciona. Com o Point primeiro, quem compara é o ColorPoint, e a exceção aparece. O comportamento depende da ordem dos elementos, não dos valores.
A saída

Composição
em vez de herança

Tem um Point

Não é subtipo.
Define sua própria ordem.

View

asPoint() devolve o Point
para quem precisa dele.

Mesma recomendação do livro para equals: escreva uma classe não relacionada com um campo do tipo original e um método de view. Sem relação de subtipo, não há contrato da superclasse para defender.

Vários campos

Do campo mais
significativo ao menos

areaCode → prefix → lineNum

Use Integer.compare, nunca < e > nem subtração.

Compare o campo mais importante primeiro. Se o resultado não for zero, ele decide; senão, siga para o próximo. Desde o Java 7, os métodos estáticos compare das classes wrapper substituem os operadores relacionais, que o livro chama de verbosos e propensos a erro.

Um caso real

Subtração transborda

return this.priority() - other.priority();

open-workflow-specification/sdk-java #1799

O livro mostra o comparator baseado na diferença de hashCode como exemplo do que não fazer: a subtração transborda o int e viola a transitividade. No SDK Java do Open Workflow, ServicePriority fazia exatamente isso, e ele decide qual implementação é escolhida via ServiceLoader em quase todos os pontos de extensão. Quem retornasse Integer.MIN_VALUE para sempre vencer perdia, sem nenhuma exceção. Issue 1797; corrigido no PR 1799.

Recapitulando

Item 14

  • Comparable declara uma ordenação natural
  • Respeite reflexividade, simetria e transitividade
  • Prefira ser consistente com equals
  • Contrato quebrado quebra TreeSet, sort e binarySearch
  • Para estender com valor, use composição
  • Use Integer.compare ou Comparator, nunca subtração
Retome os exemplos: CaseInsensitiveString, Glossary, Rank, ColorPoint, PhoneNumber e ServicePriority.
