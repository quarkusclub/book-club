Mixin and marker

Cloneable does not declare clone

Mixin

Adds a capability.
Comparable enables comparison.

Cloneable

Zero methods.
Object.clone remains protected.

Implementing the marker does not expose a copy operation.

Connect to Item 20. A mixin adds a capability without a particular superclass and does not require default methods. Describable exposes describe through its interface. Cloneable permits Object.clone copying without declaring the operation. protected does not permit invocation on an arbitrary receiver merely because every class extends Object. Reflection can locate a method without permission to invoke it.

The contract

Three conventions

x.clone() != x

x.clone().getClass() == x.getClass()

x.clone().equals(x)

Another instance · same type · equality depends on equals

These are general expectations for overrides, not absolute requirements or compiler-checked postconditions. The specific Object.clone algorithm creates another instance of the runtime class when it accepts the receiver. Object.equals treats distinct objects as unequal. PhoneNumber defines component equality; Stack inherits identity equality.
The test: equals may compare identity
contract/PhoneNumberTest.java
Reuse Stack to demonstrate Object.equals without another class. The clone is distinct and unequal under this identity equality model.
The simple case

PhoneNumber: same values,
another instance

Object.clone copies fields without running constructors.

Primitives: copied values.
References: the same objects.

PhoneNumber has only primitive fields, so field copying preserves its state. Covariant PhoneNumber return avoids a client cast. Constructors and instance initializers do not run; static does not become separate instance state and transient does not alter copying. The immutable class implements clone here only to teach the mechanism: new immutable values can usually be shared.

Inheritance

Constructing the base class
loses the subtype

new Parent() is still Parent,
even when the original is Child.

The super.clone chain preserves the runtime class.

Parent is the role of InheritanceExample here. brokenClone demonstrates constructing the base. The correct implementation chains super.clone to Object. The base keeps clone protected without implementing Cloneable; Child opts into the marker and exposes a public covariant return. A base can also prevent cloning through a protected final throwing method. Avoid imposing the marker on new hierarchies.

Mutable references

Stack: another stack,
the same array?

size is copied, but elements still reaches the same array after super.clone. pop clears a removed slot; in a shallow copy that also clears a slot still used by the original. Copying the array fixes storage ownership, without deep-copying all payloads.

Arrays

New array.
The same elements.

StringBuilder[] copies references to the builders.

To isolate their state, copy each mutable element too.

Arrays have public clone, their own return type and no checked exception. An int[] has independent slots; reference arrays retain objects. In int[][] only the outer array is new. Deep copying separates mutable state according to policy; immutable values may be shared. Cycles and repeated references require an additional policy.

Linked structures

HashTable: new buckets,
shared nodes

Copying the bucket array does not copy
the nodes in its chains.

The correction must rebuild every node.

The structure has a bucket array and Entry chains. Aa and BB have equal hashes and produce a real collision. Copying only buckets retains shared nodes; updating the tail can change the original. The table only provides put and get to expose this behavior. Keys and values are immutable strings. This is not java.util.Hashtable implementation.
An iterative copy of each chain
mutable/HashTable.java
mutable/HashTable.java
The loop rebuilds nodes and clone visits every bucket. Recursion uses one call per node and can cause StackOverflowError on long chains; iteration uses constant auxiliary space besides new nodes. Rebuilding through insertion is possible too, but must not call overridable methods while preparing the clone.
The test: head and tail updates
mutable/HashTableTest.java
The bucket-only copy changes the original tail. The corrected copy updates its head and tail without changing original values. All outcomes are deterministic.
Implementation constraints

Preserve the invariants

Final references

final does not freeze a list.
clone cannot replace that field.

Checked exception

Without Cloneable, Object.clone throws
CloneNotSupportedException.

A final mutable-list reference remains shared after shallow copying and cannot be reassigned in clone. Do not automatically weaken final to accommodate cloning. A clone under preparation must not call overridable methods: subclass code can run before its references are repaired. In thread-safe classes, copying must follow the writers synchronization protocol; Object.clone alone provides neither synchronization nor an atomic snapshot. Explain these concerns without extra classes or race simulations.

Alternatives

Construct the copy explicitly

Copy constructor

new Account(original)

Copy factory

Account.copyOf(original)

Normal construction, final fields and a class-defined copy policy.

Account copies its list through construction while retaining final. Immutable strings may be shared. No technique automatically guarantees a deep copy. Constructors do not preserve subtypes polymorphically; factories can choose another representation. Immutable values normally need no copying. As a backend extension, distinguish entity snapshots that may keep an ID from new entities requiring an identity and lifecycle policy. No additional demonstration entity is needed.

Recap

Item 13

  • Cloneable does not expose a public operation
  • Object.clone makes a shallow copy
  • Copy mutable state that requires independence
  • Preserve invariants and runtime class
  • Favor constructors and factories in new models
Revisit the examples: field copying suffices for PhoneNumber, Stack needs another array, and HashTable needs new nodes. Existing contracts may require Cloneable. Arrays are a suitable clone use case. The recommendation is not an absolute prohibition.
