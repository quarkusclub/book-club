Mixin e marcador

Cloneable não declara clone

Mixin

Acrescenta uma capacidade.
Comparable permite comparar.

Cloneable

Zero métodos.
Object.clone continua protected.

Implementar o marcador não publica uma operação de cópia.

Relacionar ao Item 20. Uma mixin acrescenta uma capacidade sem exigir uma superclasse específica; não precisa de métodos default. Describable expõe describe pelo tipo da interface. Cloneable autoriza a cópia de Object.clone, mas não declara o método. protected não permite invocá-lo em qualquer receptor só porque toda classe herda Object. Reflection pode localizar o método sem ter acesso para invocá-lo.

O contrato

Três convenções

x.clone() != x

x.clone().getClass() == x.getClass()

x.clone().equals(x)

Outra instância · mesmo tipo · igualdade depende de equals

São expectativas gerais para sobrescritas, não exigências absolutas nem pós-condições verificadas pelo compilador. O algoritmo específico de Object.clone, quando aceita o receptor, cria outra instância da classe concreta. Com Object.equals, objetos distintos não são iguais. PhoneNumber define igualdade por componentes; Stack herda igualdade por identidade.

O caso simples

PhoneNumber: mesmos valores,
outra instância

Object.clone copia os campos, sem executar construtores.

Primitivos: valores copiados.
Referências: os mesmos objetos.

PhoneNumber tem apenas campos primitivos. A cópia campo a campo já preserva seu estado. O retorno covariante PhoneNumber evita cast no cliente. Construtores e inicializadores de instância não são executados; static não vira estado separado e transient não altera a cópia. A classe é imutável e só implementa clone aqui para estudar o mecanismo: novos valores imutáveis normalmente podem ser compartilhados.

A classe final implementa Cloneable e chama diretamente Object.clone. Por isso a ausência do marcador não pode ocorrer nesse caminho e a exceção verificada é convertida em AssertionError, preservando a causa.

Herança

Instanciar a classe base
perde o subtipo

new Parent() continua sendo Parent,
mesmo quando o original é Child.

A cadeia de super.clone preserva a classe real.

Parent é o papel da classe InheritanceExample neste exemplo. brokenClone demonstra a variante que instancia a base. A implementação correta encadeia super.clone até Object. A base mantém o método protegido sem implementar Cloneable; Child opta pelo marcador e amplia o retorno para público e covariante. Uma base também pode impedir clonagem com método protegido final que lança a exceção. Não imponha o marcador a novas hierarquias.

Referências mutáveis

Stack: outra pilha,
o mesmo array?

size é copiado, mas a referência elements continua levando ao mesmo array após super.clone. pop limpa a posição removida; no clone superficial isso também limpa um slot ainda usado pelo original. A correção é copiar o array. É independência da estrutura, não cópia profunda de todos os elementos.
A falha e a correção do array interno

mutable/Stack.java
shallowCopy é a variante deliberadamente incorreta. clone usa essa cópia inicial e substitui elements por outro array. pop continua limpando o slot para evitar referências obsoletas.
O teste: pop não pode corromper o original

Arrays

Array novo.
Os mesmos elementos.

StringBuilder[] copia referências aos builders.

Para isolar seus estados, copie também cada elemento mutável.

Arrays têm clone público, retorno do próprio tipo e nenhuma exceção verificada. Um int[] tem posições independentes; um array de referências mantém os objetos. Em int[][] apenas o array externo é novo. Copiar profundamente significa separar o estado mutável necessário segundo a política; valores imutáveis podem ser compartilhados. Grafos com ciclos ou referências repetidas exigem uma política adicional.
O teste: copiar o array e copiar o elemento
mutable/StackTest.java
A mutação pelo array clonado muda o original para AB. Criar outro StringBuilder isola a mudança seguinte: a cópia fica ABC e o original continua AB.
Estruturas encadeadas

HashTable: buckets novos,
nós compartilhados

Copiar o array de buckets não copia
os nós das suas cadeias.

A correção precisa reconstruir todos os nós.

A estrutura tem um array de buckets e cadeias Entry. Aa e BB têm o mesmo hash e produzem uma colisão real. Copiar só buckets ainda compartilha os nós; atualizar a cauda pode mudar o original. A tabela foi reduzida a put e get para mostrar isso. As chaves e valores são strings imutáveis. Não é a implementação de java.util.Hashtable.
Uma cópia iterativa de cada cadeia
mutable/HashTable.java
mutable/HashTable.java
O laço reconstrói os nós e o clone percorre todos os buckets. Recursão usaria uma chamada por nó e poderia causar StackOverflowError em cadeias longas; a iteração usa espaço auxiliar constante além dos nós novos. Uma reconstrução via inserção também é possível, mas não deve chamar métodos sobrescrevíveis durante a preparação do clone.
O teste: alterações na cabeça e na cauda
mutable/HashTableTest.java
A cópia só de buckets altera a cauda original. A cópia corrigida muda cabeça e cauda sem afetar os valores do original. Todos os resultados são determinísticos.
Cuidados na implementação

Preserve as invariantes

Referências final

final não torna a lista imutável.
clone não pode substituir esse campo.

Exceção verificada

Sem Cloneable, Object.clone lança
CloneNotSupportedException.

Uma referência final para uma lista mutável continua compartilhada após cópia superficial e não pode ser reatribuída no clone. Não enfraqueça final automaticamente para acomodar clonagem. Um clone em preparação também não deve chamar métodos sobrescrevíveis: uma subclasse pode executar antes de reparar suas referências. Em classes thread-safe, a cópia deve respeitar o protocolo de sincronização das escritas; Object.clone não oferece sincronização nem snapshot atômico sozinho. Esses cuidados são explicados sem adicionar classes ou simular corridas.
O teste: restrições da linguagem e da API

contract/CloneableDemoTest.java
O javac rejeita o fixture que tenta substituir uma referência final no método de cópia. A chamada real a Object.clone sem marcador lança a exceção verificada. A conversão para AssertionError em PhoneNumber depende das premissas daquela implementação; não é regra universal.
Alternativas

Construa a cópia explicitamente

Copy constructor

new Account(original)

Copy factory

Account.copyOf(original)

Construção normal, campos final e política de cópia definida pela classe.

Account copia a lista pelo construtor e mantém o campo final. Strings imutáveis podem ser compartilhadas. Nenhuma técnica garante cópia profunda automaticamente. Construtores não preservam subtipos por polimorfismo; factories podem escolher outra representação. Imutáveis normalmente dispensam cópia. Como complemento de backend, diferencie snapshot de entidade, que pode preservar ID, de nova entidade, que exige política explícita de identidade e ciclo de vida. Não precisamos de outra entidade demonstrativa para isso.
Inicializar uma nova lista mantendo final
alternatives/Account.java
O construtor comum cria uma ArrayList. O construtor de cópia delega a ele, e a factory delega ao construtor de cópia. A política é independente para a lista e compartilhada para as strings.
O teste: cada cópia possui sua própria lista
alternatives/AccountTest.java
Adicionar um rótulo a uma cópia não altera o original nem a outra cópia. O teste também verifica que esta factory retorna outra instância; o nome copyOf sozinho não garante isso para toda API.
Recapitulando

Item 13

  • Cloneable não oferece uma operação pública
  • Object.clone faz uma cópia superficial
  • Copie o estado mutável que precisa de independência
  • Preserve as invariantes e a classe concreta
  • Prefira construtores e factories em novos modelos
Retome os exemplos: PhoneNumber basta copiar campos; Stack precisa de outro array; HashTable precisa de novos nós. Cloneable pode ser exigido por contratos existentes. Arrays são um caso adequado para clone. A recomendação não é uma proibição absoluta.
