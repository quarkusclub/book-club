The tempting shortcut

A constant hash

It compiles. It can satisfy the contract.
But every instance receives the same hash.

A correct contract does not guarantee good distribution.

Returning 42 does not cause an error by itself. Equal objects both return 42, so the required implication holds. The problem is that unequal objects also always receive 42. A constant hash does not make equals incorrect: it harms distribution.

The fundamental rule

Equal.

a.equals(b) == true
requires equal hashes.

If a.equals(b) is true, a.hashCode() and b.hashCode() must agree. The converse is not required. Repeated calls must also keep the result while state used by equals remains unchanged; the number need not persist between application runs.
THE CONSEQUENCE

Equal, but not found

The collection uses hashCode before confirming with equals.

HashMap uses the hash to select candidates; equals determines equality among candidates. If equal objects have inconsistent hashes, a lookup can fail. Even objects in the same bucket may have different full hashes and be rejected before equals.

Object fields

The same notion of equality

Use the hash of the object participating in equals.

If equality uses a canonical value, hashing must use it too.

For an object field, use its corresponding hash; Objects.hashCode handles null if null is allowed. This example defines equality using stripped lowercase text with Locale.ROOT. Do not conflate this rule with equalsIgnoreCase over all Unicode.

Why 31?

Odd and prime

ODD

Preserves bits

Even multipliers can discard information through overflow.

PRIME

A tradition

A useful choice with no magical distribution guarantee.

31

Simple

Multiplication by 31 equals shifting by 5 and subtracting.

Do not turn this into a mathematics lecture. In int arithmetic an even multiplier can lose the highest bit: multiplying by a power of two shifts bits. Choosing a prime is also traditional; primality does not guarantee a good hash. The shift equivalence does not mean we should handwrite the optimization.
The test: a bit lost by an even multiplier
objects/HashIngredientsTest.java
Integer.MIN_VALUE contains only the highest bit. Multiplication by 32 overflows to zero; multiplication by 31 preserves a distinction from zero. This narrow demonstration supports the book's explanation without claiming 31 solves every collision.
The convenient alternative

Objects.hash

Less code to combine the fields.

Convenience can have a cost: varargs, an array and boxing.

Objects.hash(Object... values) receives objects. Calling it with primitives involves boxing and a varargs array. It can be slower, but do not promise a measured difference: the JIT may eliminate work and boxing may reuse wrappers. This alternative need not return the same number as the previous recipe, only respect its own equality.

CACHE WHEN IT MAKES SENSE

Calculate once, reuse

Immutable state · expensive calculation · repeated calls

First show the notes' caching pattern in PhoneNumber, but explain that three fields make the calculation cheap: the extra field and check probably do not pay off. Then use Document to show larger state requiring traversal.
The pattern: lazy caching
caching/CachedPhoneNumber.java
The counter is demonstration instrumentation only. Logical state has final fields; the derived cache does not participate in equality. We count calculations in sequential calls. This code does not promise only one calculation under concurrent calls.
The test: a nonzero hash is calculated once
caching/CachedPhoneNumberTest.java
Before the first call, the counter is zero. After repeated calls, it remains one and all results agree. This proves reuse, not a performance advantage for PhoneNumber.
The sentinel has a peculiarity

What if the real hash is zero?

Zero also means “not calculated”.
The hash will be recalculated on later calls.

The value stays correct. The contract stays valid.

A zero hash is permitted. This recipe produces zero for 0, 0, 0. The field remains zero after calculation, so the next call recalculates. This reduces caching benefit in this case but never changes equality or the returned hash.
The test: recalculating zero keeps the contract
caching/CachedPhoneNumberTest.java
Two equal instances return zero; the first computes twice. This test demonstrates the peculiarity without inventing timing results.
When state is larger

An immutable Document

A thousand paragraphs. Many hash queries.

One traversal reused by subsequent calls.

Document stores an immutable copy of the String list. The list hash considers its elements and their order. Even if Strings cache their own hashes, the list must be traversed to combine them. Counting traversals is deterministic evidence of avoided work, not a latency benchmark.
The same pattern, with a collection
caching/Document.java
The cache reuses the complete list hash. Do not remove paragraphs from the hash to make calculation faster. Immutable logical state permits reusing the result.
The test: one traversal, one hundred reuses
caching/DocumentTest.java
A thousand elements are traversed on the first call. The next hundred return the same value with the counter at one. An equivalent Document also produces the same hash. No System.nanoTime measurement is needed.
The condition: protect state
caching/Document.java
List.copyOf detaches internal state from the mutable input list. Strings are already immutable. The caller therefore cannot change state after caching its hash. The counter and cache are derived state, not equality components.
The test: the external list may change
caching/DocumentTest.java
Modifying the original list does not change Document. The test verifies equality with the original snapshot, the same hash and no new traversal.
Optimize without impoverishing

Do not omit significant data

A cheaper hash can concentrate different values.
Consider all relevant logical state.
Omitting a significant field can still satisfy the equal-object requirement but worsen distribution among different values. Do not conflate legality with quality. PhoneNumber considers all three fields; Document considers all paragraphs and their order.
The test: each field participates

Individual changes to area code, prefix and line change equality and, for these examples, hashing. The assertion keeps the distinction between contract and distribution explicit.

Good distribution

  • Bucket 0 · A
  • Bucket 1 · B
  • Bucket 2 · C

Constant hash

  • Same bucket · A, B, C
  • More candidates to compare
  • HashSet uses HashMap internally
This is a conceptual picture: the bucket is not simply the number returned by hashCode. HashMap spreads bits and considers table capacity. The next test illustrates OpenJDK's spreading for a table of sixteen slots; it does not inspect private storage or promise that algorithm as an API.
The test: one sample, one bucket versus sixteen
distribution/ConstantHashPhoneNumberTest.java
The selected sixteen-number sample occupies sixteen buckets in this implementation model, versus one with a constant hash. This proves distribution for the sample, not universal uniformity or running times. The helper uses OpenJDK's spreading and mask.
Complexity in context

Collisions cost

Long chains can require linear searches.
Modern HashMap can use trees under specific conditions.

Mitigation is no license to use a poor hash.

With list buckets, a bad operation can scan n entries and a sequence of n insertions can accumulate quadratic work. Since Java 8, tree bins mitigate some concentrations when table and bucket size conditions hold. With identical hashes, key ordering also matters: do not promise universal O(log n) for arbitrary keys. Details and source: https://github.com/openjdk/jdk25u/blob/master/src/java.base/share/classes/java/util/HashMap.java . The distribution test is not a benchmark of that complexity.
Historical context

Induced collisions

External strings can concentrate work in a hash table.

An example of why distribution matters.

There is a history of collision attacks in web applications: externally controlled inputs were chosen to collide and consume hash-table processing. CERT documented the issue in 2011: https://www.kb.cert.org/vuls/id/903934/ . Aa and BB are only a minimal demonstration of String collision, not an attack reproduction or a claim that every current Java application is vulnerable.
The test: different strings, equal hash
distribution/StringCollisionTest.java
Platform classes also allow collisions. The set keeps both Strings. This test proves only that behavior; the historical context is supported by the source in the notes.
Future compatibility

Document the contract

Avoid promising your internal hashCode algorithm.

Integer and String already specify results in their APIs.

If clients depend on a documented formula, changing implementation can break expectations. Integer documents its int value as its hash; String documents its formula. These show existing public commitments without inventing a historical breaking-change incident. For new classes, documenting equality and hash obligations preserves room to improve distribution. Sources: https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Integer.html#hashCode() and https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html#hashCode() .
