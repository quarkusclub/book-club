Sempre sobrescreva hashCode ao sobrescrever equals

O atalho tentador

Um hash constante

Compila. Pode cumprir o contrato.
Mas todas as instâncias recebem o mesmo hash.

Contrato correto não garante boa distribuição.

Retornar 42 não causa um erro por si só. Se dois objetos são iguais, ambos retornam 42, portanto a implicação exigida pelo contrato é respeitada. O problema é que objetos diferentes também recebem sempre 42. Não dizer que o hash constante torna equals incorreto: ele prejudica a distribuição.
Mesmo equals; sempre 42
distribution/ConstantHashPhoneNumber.java
A classe delega a igualdade ao PhoneNumber completo. Nenhum campo significativo foi retirado do equals; apenas o hash é constante. Mostrar os dois métodos juntos.
O teste: colidir ainda funciona
distribution/ConstantHashPhoneNumberTest.java
O conjunto guarda dois números diferentes, encontra uma instância equivalente e recusa uma duplicata lógica. O mapa também encontra o valor certo. Isso prova a semântica, não eficiência: não há benchmark aqui.

PhoneNumber(313, 414, 533)

Um valor.

PhoneNumber(314, 413, 533)

Outro valor. Idealmente, outro hash.

Estes são os números das notas. Queremos mitigar colisões, não prometer que todo objeto diferente terá hash diferente. Um int tem um espaço finito de resultados; colisões são permitidas. A receita que veremos produz hashes diferentes para estes dois exemplos concretos.
A regra fundamental

Iguais.

a.equals(b) == true
exige hashes iguais.

Se a.equals(b) é true, obrigatoriamente a.hashCode() e b.hashCode() concordam. O contrário não é obrigatório. Chamadas repetidas também precisam manter o resultado enquanto o estado usado pelo equals não mudar; não há obrigação de repetir o número entre execuções da aplicação.
A CONSEQUÊNCIA

Igual, mas não encontrado

A coleção usa hashCode antes de confirmar com equals.

HashMap usa o hash para selecionar candidatos; equals resolve a igualdade entre candidatos. Se hashes de objetos iguais não concordam, uma busca pode falhar. Até objetos no mesmo bucket podem ter hashes completos diferentes e ser descartados antes do equals.
O equals está correto; falta hashCode
contract/PhoneNumberWithoutHashCode.java
Esta classe tem os três campos finais e a validação de faixas do PhoneNumber. O método exibido encerra a classe: não existe override de hashCode. A implementação herdada continua sendo a de Object.
O teste: igualdade por valor, hash de identidade
contract/BrokenHashCodeTest.java
Não exigir que duas instâncias tenham hashes de identidade diferentes: elas podem colidir. O teste demonstra que o hash continua sendo o de identidade. Para provar a falha de busca de forma estável, o próximo exemplo controla os hashes.
A falha com hashes controlados
contract/PhoneNumberBrokenHashCode.java
A igualdade ainda delega ao mesmo número. O segundo argumento do construtor simula hashes de identidade distintos; não faz parte do estado lógico. Essa é uma implementação deliberadamente quebrada para garantir que a demonstração seja reproduzível.
O teste: equals concorda, a busca falha
contract/BrokenHashCodeTest.java
Usar hashes 1 e 2 evita depender de sorte na JVM. contains e get são chamados nas coleções reais; o teste não substitui a busca por uma varredura usando equals. As duas instâncias são iguais, mas o conjunto pode até aceitar ambas.
A correção: o mesmo estado lógico
contract/PhoneNumber.java
Os três campos usados por equals também alimentam hashCode. Mostrar o conjunto dos métodos agora; a receita com Short.hashCode e o multiplicador 31 será detalhada adiante.
O teste: a nova instância é encontrada
contract/PhoneNumberTest.java
Com o contrato corrigido, HashSet e HashMap encontram uma nova instância com o mesmo valor. add também recusa a duplicata lógica. É a mesma consequência prática que encerrava o Item 10.

Objetos diferentes na memória, iguais por valor, com o mesmo hash em chamadas repetidas. Esta é a obrigação do contrato, e não uma propriedade opcional de distribuição.
A volta não vale

Mesmo hash não implica igualdade

313, 414, 533
313, 413, 564
Valores diferentes. O mesmo hash nesta receita.
Reduzir o prefixo em 1 e aumentar a linha em 31 faz as contribuições se cancelarem nesta fórmula. Isso é uma colisão válida. HashSet usa equals para manter os dois valores separados. Não ensinar hashCode como identificador único.
O teste: dois valores sobrevivem à colisão
contract/PhoneNumberTest.java
O teste afirma hash igual e equals diferente, depois verifica que o conjunto guarda ambos e consegue buscar um deles por uma instância equivalente.
Campos que são objetos

A mesma noção de igualdade

Use o hash do objeto que participa do equals.

Se equals usa um valor canônico, hashCode também precisa usá-lo.

Para um campo objeto, usar seu hash correspondente; se null for um valor permitido, Objects.hashCode trata esse caso. O exemplo define a igualdade por texto normalizado com strip e lowercase em Locale.ROOT. Não confundir essa regra com equalsIgnoreCase para todo Unicode.
Um valor canônico para equals e hashCode
objects/CanonicalLabel.java
O construtor do record normaliza o componente antes de armazená-lo. O equals gerado compara esse componente canônico; hashCode chama o hash da mesma String. Nenhuma comparação com String de outro tipo é adicionada.
O teste: variações encontram o mesmo valor
objects/CanonicalLabelTest.java
Espaços nas pontas e caixa diferente não mudam o valor segundo a regra desta classe. O teste prova igualdade, hash igual e busca no HashSet.
Campos primitivos

Type.hashCode(campo)

Short · Integer · Boolean

O método estático recebe o primitivo correspondente.

Seguir a ideia do livro: Short.hashCode(areaCode), Integer.hashCode(age), Boolean.hashCode(active). Usar a classe wrapper como dona do método estático não significa que o argumento precisa sofrer boxing.
O teste: hashes de primitivos
objects/HashIngredientsTest.java
Comparar os resultados reais da API. A chamada estática recebe short, int ou boolean; não é equivalente a construir um wrapper para chamar um método de instância.
A RECEITA DO LIVRO

PhoneNumber e 31

Combine todos os campos significativos, em uma ordem estável.

Voltar ao PhoneNumber principal, com três shorts. A ordem dos termos afeta a distribuição; não é necessário copiar a ordem das comparações em equals. É necessário manter a mesma regra entre instâncias iguais.
Três campos; uma combinação
contract/PhoneNumber.java
Iniciar com o hash do código de área, multiplicar por 31 antes de adicionar prefixo e linha. Esta ordem distingue os dois números das notas. Não prometer ausência de colisões.
O teste: distribuição neste par concreto
contract/PhoneNumberTest.java
A assertion de hashes diferentes vale para estes dois valores e para esta implementação. Não é um requisito universal para objetos diferentes. Isso fica registrado também na descrição da assertion.
Por que 31?

Ímpar e primo

ÍMPAR

Preserva bits

Multiplicadores pares podem descartar informação com overflow.

PRIMO

Uma tradição

Uma escolha útil, sem garantia mágica de distribuição.

31

Simples

Multiplicar por 31 equivale a deslocar por 5 e subtrair.

Não transformar em uma aula de matemática. Em aritmética int, um multiplicador par pode perder o bit mais alto: multiplicar por uma potência de dois equivale a deslocar bits. O fato de 31 ser primo também tem caráter tradicional; primo não garante um bom hash. A equivalência com deslocamento não significa que precisamos escrever a otimização manualmente.
O teste: um bit perdido pelo multiplicador par
objects/HashIngredientsTest.java
Integer.MIN_VALUE contém apenas o bit mais alto. Multiplicá-lo por 32 produz zero por overflow; multiplicar por 31 mantém uma distinção em relação a zero. Essa demonstração estreita sustenta a explicação do livro, sem alegar que 31 resolve todas as colisões.
A alternativa conveniente

Objects.hash

Menos código para combinar os campos.

Conveniência pode ter custo: varargs, array e boxing.

Objects.hash(Object... values) recebe objetos. A chamada com primitivos envolve boxing e um array de varargs. Pode ser mais lenta, mas não prometer uma diferença medida: o JIT pode eliminar trabalho e boxing pode reutilizar wrappers. Não precisamos que esta alternativa retorne o mesmo número da receita anterior, apenas que respeite seu próprio equals.
A alternativa das notas
objects/PhoneNumberWithObjectsHash.java
Manter a ordem do exemplo: linha, prefixo e código de área. Essa ordem também é válida. Como os três campos são iguais em instâncias equivalentes, o resultado será igual nelas.
O teste: a conveniência mantém o contrato
objects/PhoneNumberWithObjectsHashTest.java
O teste verifica a igualdade, o hash e uma busca real no mapa. Não compara hashes de classes diferentes: objetos de tipos diferentes não são definidos como iguais nestes exemplos.

Boxing

boolean → Boolean
int → Integer

Unboxing

Boolean → boolean
Integer → int

As direções são opostas. No Objects.hash, o ponto principal é boxing dos primitivos para caber em Object[], junto com o array de varargs. Não atribuir esse custo ao unboxing.
O teste: ida e volta entre primitivo e wrapper
objects/HashIngredientsTest.java
As atribuições tornam visível a direção de cada conversão. Integer e Boolean são tipos de referência; int e boolean são primitivos.
O teste: o array de valores com boxing

A API Objects.hash calcula como Arrays.hashCode sobre o array de argumentos. Mostrar que os shorts viram Short. Este teste demonstra a equivalência funcional e os tipos, não quantifica alocações em uma JVM otimizada.
CACHE QUANDO FIZER SENTIDO

Calcular uma vez, reutilizar

Estado imutável · cálculo caro · chamadas repetidas

Mostrar primeiro o padrão de cache das notas no PhoneNumber, mas explicar que três campos tornam o cálculo barato: provavelmente não compensa o campo adicional e a verificação. Em seguida, usar Document para mostrar um estado maior que exige uma travessia.
O padrão: cache preguiçoso
caching/CachedPhoneNumber.java
O contador é apenas instrumentação da demonstração. O estado lógico tem campos finais; o cache derivado não participa do equals. Medimos cálculos em chamadas sequenciais. Este código não promete que apenas uma thread fará o cálculo em chamadas concorrentes.
O teste: o hash não zero é calculado uma vez
caching/CachedPhoneNumberTest.java
Antes da primeira chamada, o contador é zero. Depois de várias chamadas, permanece um e todos os resultados concordam. Isso prova reutilização, não uma vantagem de performance para PhoneNumber.
A sentinela tem uma peculiaridade

E se o hash real for zero?

Zero também significa “não calculado”.
O hash será recalculado nas próximas chamadas.

O valor continua correto. O contrato continua válido.

Não existe proibição de hash zero. Para 0, 0, 0, esta receita produz zero. O campo continua zero após calcular, então a próxima chamada recalcula. Isso reduz o benefício do cache nesse caso, mas nunca muda a igualdade ou o hash retornado.
O teste: recalcular zero não quebra o contrato
caching/CachedPhoneNumberTest.java
Duas instâncias iguais retornam zero; a primeira calcula duas vezes. O teste demonstra a peculiaridade sem inventar um resultado de tempo.
Quando o estado é maior

Um Document imutável

Mil parágrafos. Muitas consultas ao hash.

Uma travessia reutilizada nas chamadas seguintes.

O Document guarda uma cópia imutável da lista de Strings. O hash da lista considera seus elementos e a ordem. Mesmo que Strings possam ter seu próprio cache, a lista precisa ser percorrida para combinar esses hashes. Contar travessias é uma evidência determinística do trabalho evitado, não um benchmark de latência.
O mesmo padrão, com uma coleção
caching/Document.java
O cache reaproveita o hash da lista completa. Não retirar parágrafos do hash para acelerar o cálculo. Imutabilidade do estado lógico é o que permite reutilizar o resultado.
O teste: uma travessia, cem reutilizações
caching/DocumentTest.java
Mil elementos são percorridos na primeira chamada. As cem seguintes retornam o mesmo valor, com contador igual a um. Um Document equivalente também produz o mesmo hash. Nenhuma medição de System.nanoTime é necessária.
A condição: proteger o estado
caching/Document.java
List.copyOf desconecta a lista interna da lista mutável recebida. Strings já são imutáveis. Assim o chamador não consegue alterar o estado depois que o hash foi cacheado. O contador e o cache são derivados, não componentes de igualdade.
O teste: a lista externa pode mudar
caching/DocumentTest.java
Modificar a lista original não muda o Document. O teste verifica a igualdade com o snapshot original, o mesmo hash e a ausência de uma nova travessia.
Otimizar sem empobrecer

Não omita dados significativos

Um hash mais barato pode concentrar valores diferentes.
Considere todo o estado lógico relevante.
Omitir um campo significativo pode ainda cumprir a obrigação de hashes iguais para objetos iguais, mas piora a distribuição entre objetos diferentes. Não confundir legalidade com qualidade. Nosso PhoneNumber considera os três campos; nosso Document considera todos os parágrafos e sua ordem.
O teste: cada campo participa

As mudanças isoladas em código de área, prefixo e linha mudam equals e, nesses exemplos, também o hash. A distinção entre contrato e distribuição continua explícita na assertion.

Boa distribuição

  • Bucket 0 · A
  • Bucket 1 · B
  • Bucket 2 · C

Hash constante

  • Mesmo bucket · A, B, C
  • Mais candidatos para comparar
  • HashSet usa HashMap internamente
O desenho é conceitual: o bucket não é simplesmente o número retornado por hashCode. HashMap espalha bits e considera a capacidade da tabela. O teste seguinte ilustra o espalhamento do OpenJDK para uma tabela de 16 posições; não inspeciona a tabela privada nem promete esse algoritmo como API.

O conjunto de 16 números escolhido ocupa 16 buckets no modelo desta implementação, contra um com hash constante. Isso prova a distribuição desta amostra, não uniformidade universal ou tempos de execução. A função auxiliar usa o espalhamento e a máscara do OpenJDK.
Complexidade com contexto

Colisões custam

Cadeias longas podem exigir buscas lineares.
HashMap moderno pode usar árvores em condições específicas.

Mitigação não é uma licença para usar um hash ruim.

Com buckets em lista, uma operação ruim pode percorrer n entradas e uma sequência de n inserções pode somar trabalho quadrático. Desde Java 8, tree bins mitigam certas concentrações quando a tabela e o bucket atingem condições de tamanho. Para hashes idênticos, a capacidade de ordenar as chaves também importa: não prometer O(log n) universal para qualquer chave. Detalhes e fonte: https://github.com/openjdk/jdk25u/blob/master/src/java.base/share/classes/java/util/HashMap.java . Não usamos o teste de distribuição como benchmark dessa complexidade.
Um contexto histórico

Colisões provocadas

Strings externas podem concentrar o trabalho de uma tabela.

Um exemplo de por que a distribuição importa.

Há um contexto histórico de collision attacks em aplicações web: entradas controladas externamente eram escolhidas para gerar colisões e consumir processamento nas tabelas. O CERT documentou o problema em 2011: https://www.kb.cert.org/vuls/id/903934/ . Aa e BB são só uma demonstração mínima de colisão de Strings, não uma reprodução de ataque nem uma alegação de vulnerabilidade de toda aplicação Java atual.
O teste: Strings diferentes, hash igual
distribution/StringCollisionTest.java
Colisão é permitida também nas classes da plataforma. O conjunto mantém as duas Strings. O teste comprova só esse comportamento, enquanto o contexto histórico está apoiado na fonte das notas.
Compatibilidade futura

Documente o contrato

Evite prometer o algoritmo interno do seu hashCode.

Integer e String já especificam resultados na API.

Se os clients passam a depender de uma fórmula documentada, mudar a implementação pode quebrar expectativas. Integer documenta o próprio valor int como hash; String documenta sua fórmula. Esses exemplos mostram compromissos públicos já existentes, sem inventar um episódio histórico de quebra. Para novas classes, documentar a igualdade e as obrigações de hash preserva espaço para melhorar distribuição. Fontes: https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Integer.html#hashCode() e https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html#hashCode() .
