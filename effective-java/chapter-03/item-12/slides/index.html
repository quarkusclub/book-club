O problema

Qual telefone falhou?

Logs · mensagens de erro · debugging

Uma representação útil permite inspecionar o estado rapidamente.

toString é um dos métodos mais importantes para facilitar debugging. Uma linha como Failed to connect to seguida do objeto deveria ajudar a entender qual número estava em uso. Vamos ver a diferença com o mesmo estado lógico, mantendo os exemplos pequenos.
A implementação herdada

ClassName@hexHash

Nome da classe + hash em hexadecimal.
Pouca informação sobre o valor do telefone.

Não é uma descrição dos campos.

Object.toString usa getClass().getName(), @ e Integer.toHexString(hashCode()). Não afirmar que isso é necessariamente um endereço de memória ou o hash de identidade: nesta classe, hashCode já foi sobrescrito. Ainda assim o texto não descreve os três campos. Fonte: https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Object.html#toString() .
O telefone ainda sem toString útil
representation/PhoneNumberWithoutToString.java
A classe já tem equals e hashCode por delegação ao número. Sem override de toString, a saída continua sendo a herdada de Object. Não adicionar uma aplicação de negócio para demonstrar isso.
O teste: o texto herdado não mostra o telefone
representation/PhoneNumberWithoutToStringTest.java
O teste calcula a forma exata de Object.toString para esta instância, sem hardcode do hash. A concatenação inclui esse mesmo texto. O número formatado não aparece.
O mesmo estado, legível

313-414-0533

O texto revela o número.
A mensagem fica útil.

PhoneNumber deve mostrar as informações relevantes para leitura: código de área, prefixo e linha. O número 533 ocupa quatro posições e vira 0533. Essa representação é mais natural no domínio do que uma enumeração de nomes de campos.
A representação do livro
format/PhoneNumber.java
Usamos os três campos short validados, com largura 3, 3 e 4. Locale.ROOT mantém a representação documentada independente do locale de formatação da máquina. É o mesmo exemplo do livro, com esse detalhe para garantir dígitos previsíveis.
O teste: o resultado exato
format/PhoneNumberTest.java
Aqui a assertion do texto completo é apropriada porque o formato foi especificado. Ela demonstra exatamente 313-414-0533 e os doze caracteres.
Os zeros fazem parte do formato

3, 14, 123 → 003-014-0123

Larguras fixas: três, três e quatro dígitos.

O zero no especificador de formato exige padding à esquerda. O construtor rejeita valores negativos ou maiores do que a largura aceita, então um número inválido não alonga a representação. Zero é permitido no exemplo didático. Não estamos validando regras reais de telefonia.
O teste: padding e limites válidos

Mostrar o exemplo 123 → 0123 das notas e também os limites zero e máximo de cada campo. Os valores cabem em short; a validação recebe int antes do cast.
O USO IMPLÍCITO

Você já chama toString

Concatenação com String · println(Object) · %s

Não é necessário escrever object.toString() em todas essas situações. Uma concatenação com String usa a representação; println(Object) também. Para o exemplo que não implementa Formattable, String.format ou printf com %s usam toString. Não generalizar para %d ou todo especificador de formatação.

Uma decisão pública

Formato especificado vira compromisso

Se a documentação promete “XXX-YYY-ZZZZ”,
consumidores podem depender desse formato.

Mudar depois pode quebrar clients.

Ao documentar exatamente o formato, fazemos uma escolha de API. Programadores podem usá-lo em arquivos, mensagens ou conversões, e uma alteração futura pode quebrá-los. Não é uma proibição de formatos especificados; é a consequência dessa decisão. A documentação do PhoneNumber assume essa responsabilidade.
O contrato está na documentação
format/PhoneNumber.java
A Javadoc é necessária aqui: formato, larguras e padding são um contrato público não óbvio apenas pelo nome do método. A promessa é feita intencionalmente.

PhoneNumber

Formato especificado.
“XXX-YYY-ZZZZ”

Potion

Descrição útil.
Formato exato sujeito a mudança.

Esta é a diferença central das notas. PhoneNumber promete o formato. Potion declara que os detalhes exatos não são especificados e podem mudar, oferecendo um exemplo típico. Isso preserva a possibilidade de evoluir a representação, ainda mantendo informações relevantes para pessoas.
Potion: um exemplo típico, sem congelar o formato
format/Potion.java
Manter o exemplo Potion #9 com type love, smell turpentine e look india ink. A Javadoc informa que o formato pode mudar. Usar record oferece métodos de acesso simples aos componentes; a representação é explicitamente escolhida.

O teste verifica os dados relevantes, sem exigir a string completa com colchetes, rótulos e vírgulas. Os valores se distinguem neste exemplo. Não documentamos a pontuação como um contrato.
ACESSO PROGRAMÁTICO

Estado sem parse

Se o dado importa para código, ofereça um método de acesso.

Não obrigar clients a chamar toString e depois substring para recuperar código de área. O problema maior é acoplamento ao formato, fragilidade e dificuldade de evolução. O custo de parse pode ser secundário, mas não é o argumento principal. Mesmo com formato especificado, os métodos de acesso dão uma API direta e tipada.
Métodos de acesso ao valor numérico
format/PhoneNumber.java
Os accessors expõem os shorts, não uma substring da representação. O lineNumber continua 533 como número; o zero extra pertence apenas ao texto.
O teste: estado numérico sem depender do texto
format/PhoneNumberTest.java
Recuperar os três componentes diretamente e reconstruir uma instância equivalente demonstra a continuidade com equals e hashCode. Nenhum parse participa da operação.
O teste: Potion também oferece acesso direto
format/PotionTest.java
O formato da descrição pode mudar sem alterar o acesso a number, type, smell e look. São essas operações que o código consumidor deveria usar para recuperar estado.
FERRAMENTAS AJUDAM

Gerado e útil

Avalie se a representação combina com o significado do objeto.

Não dizer que toString gerado é sempre inadequado. IDEs, AutoValue e records podem produzir implementações muito melhores que Object.toString. A pergunta é se a enumeração de campos é a melhor forma de representar este objeto. Para um telefone, o formato natural pode ser melhor.
Um record gera a representação dos componentes
generated/PhoneNumberRecord.java
Nenhum método toString foi escrito neste record. O compilador gera a representação com o nome do record e os componentes. A validação mantém as mesmas faixas do telefone.
O teste: o resultado gerado é informativo
generated/PhoneNumberRecordTest.java
O texto inclui areaCode, prefix e lineNumber e seus valores. O teste não congela toda a pontuação do resultado gerado: verifica o conteúdo útil do exemplo.

Representação gerada

PhoneNumberRecord[
areaCode=313,
prefix=414,
lineNumber=533]

Representação do domínio

313-414-0533

Ambas ajudam. Esta é mais natural para um telefone.

Preservar a comparação das notas. Os dois textos são úteis para debugging. A versão pensada para o domínio apresenta o telefone como normalmente o reconhecemos. Não é necessário abandonar records para personalizar toString; uma implementação explícita também pode ser escrita em um record, como em Potion.
O teste: os mesmos componentes, outra leitura
generated/PhoneNumberRecordTest.java
O teste transfere os mesmos componentes do record para PhoneNumber e comprova as duas representações. Não adicionamos um sistema artificial de geração ou uma aplicação paralela.
Recapitulando

Item 12

  • Texto conciso com informações relevantes
  • Concatenação, println e %s usam a representação
  • Formato especificado é uma promessa pública
  • Ofereça acesso ao estado sem parse
  • Avalie o significado do texto gerado
A recomendação é sobrescrever toString em classes instanciáveis que tenham uma representação textual útil, especialmente value objects e objetos observados frequentemente em logs ou debugging. Não transformar isso numa obrigação literal de toda classe instanciável, nem ignorar uma representação adequada já herdada.
