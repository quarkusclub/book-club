O objetivo é poder desenvolver, testar e alterar componentes independentemente. Encapsulamento não acelera código automaticamente: ele permite otimizar a implementação sem exigir mudanças nos clientes. Reserve os últimos minutos para discutir as escolhas de uma API real.
01

Proteja as invariantes

A API define quais mudanças de estado são permitidas.

A API define quais mudanças de estado são permitidas.
Antes de mostrar o código

Quem pode escrever −100?

Um estoque começa com dez ingressos. A reserva não pode ser negativa nem exceder a disponibilidade.

Um campo público permite ignorar completamente essa regra.

Peça que a turma preveja o resultado do próximo teste. O problema não é só alguém escrever um valor inválido: a classe perde o controle sobre todas as atribuições feitas por clientes. Esta demonstração é sequencial; tornar o campo privado não garante thread safety.
A falha: representação pública
ExposedInventory.java
Não há uma operação de domínio entre o cliente e o estado. Até uma validação no construtor seria insuficiente para impedir a próxima atribuição.
O teste demonstra a violação
InventoryTest.java
Este teste passa porque prova que o exemplo ruim permite a corrupção. Verde aqui não significa que o design é bom.
A correção: operações controladas
Inventory.java
O estado fica privado e reserve expressa a mudança válida. A disponibilidade continua consultável. A representação pode mudar sem alterar a assinatura do contrato. Não estamos oferecendo uma implementação concorrente.
O teste prova preservação do estado
InventoryTest.java
A mesma instância recebe três tentativas inválidas e continua com dez ingressos. Mostre também validReservation durante a demonstração ao vivo para ver o caminho de sucesso.
02

Exporte o contrato

O cliente precisa do serviço, não de todos os tipos que o implementam.

O cliente precisa do serviço, não de todos os tipos que o implementam.
Tipos de nível superior

Público só quando necessário

API

TicketOffice: o cliente pede um ingresso.

Implementação

SeatFormatter: acesso de pacote.
Ticket: classe aninhada privada.

Uma classe normal de nível superior pode ser pública ou ter acesso de pacote; private e protected são opções para membros, incluindo tipos aninhados. Se um helper só serve a uma classe, considere aninhá-lo como static private. Os nomes internos não entram no tipo de retorno público.
Uma fachada, um tipo privado
TicketOffice.java
Mostre issue e a classe Ticket. A implementação privada usa campos e validação próprios, mas o cliente recebe uma String. Acesso privado é permitido dentro do mesmo tipo de nível superior e seus tipos aninhados.
O teste usa somente o contrato
TicketOfficeTest.java
Não usamos reflexão para alcançar Ticket. O teste verifica o resultado que importa ao cliente e continua válido se a implementação privada for substituída.
O pacote também é uma fronteira
SeatFormatter.java
Este helper deliberadamente demonstra acesso de pacote. Como só a fachada o utiliza hoje, ele também poderia ser aninhado. O exemplo mantém as duas alternativas visíveis para discussão.
Teste no mesmo pacote, sem API extra
TicketOfficeTest.java
Não é necessário tornar o helper público para testá-lo. A localização de src/test não muda a regra: é a declaração package que determina o acesso.
O compilador rejeita o cliente externo
AccessCompilationTest.java
A chamada a Compilation.source usa o compilador do JDK. A falha é a conclusão esperada; verificamos também o código do diagnóstico para evitar aceitar uma falha por outro motivo. O helper completo aparece em compiler/Compilation.java.
03

Escolha o menor acesso útil

Comece com private. Amplie apenas para atender um consumidor legítimo.

Comece com private. Amplie apenas para atender um consumidor legítimo.
Membros de classes

Quatro níveis, compromissos diferentes

  • private · dentro do tipo de nível superior e seus tipos aninhados
  • Sem modificador · mesmo pacote
  • protected · mesmo pacote + subclasses, com restrições
  • public · clientes com acesso ao tipo e ao pacote
Acessibilidade depende também do tipo que contém o membro e, em módulos nomeados, da leitura do módulo e da exportação do pacote. protected não significa apenas subclasses: classes comuns no mesmo pacote também podem acessá-lo. Os próximos testes verificam os casos.
Quatro métodos para experimentar
AccessRules.java
Esta classe existe apenas para a demonstração de regras da linguagem. Não é uma recomendação de criar quatro operações equivalentes numa API de produção.
Mesmo pacote: protected também funciona
AccessRulesTest.java
A classe de teste não é subclasse de AccessRules. Mesmo assim ela pode acessar packageCode e protectedCode, pois pertence ao mesmo pacote.
Private continua privado no mesmo pacote
AccessCompilationTest.java
A classe Client declara o mesmo pacote, mas é outro tipo de nível superior. privateCode continua inacessível. Isso contrasta com o acesso de pacote do slide anterior.
Subpacotes não ganham acesso de pacote
AccessCompilationTest.java
O ponto no nome do pacote organiza nomes; não cria uma relação de acesso de pai e filho. access.client é um pacote diferente de access.
Protected fora do pacote

A referência também importa

Uma subclasse externa pode acessar o membro de instância por this ou por uma referência do seu tipo, ou de um subtipo.

Uma referência tipada como a superclasse não recebe essa permissão.

É uma restrição do acesso protected a membros de instância fora do pacote, não uma regra geral sobre qualquer membro protected. O acesso precisa ocorrer no corpo da subclasse. Para um tipo público exportado, protected também é um compromisso de API com subclasses externas.
Referência Child: aceito
AccessCompilationTest.java
Peça uma previsão antes de mostrar successful true. O receptor other tem tipo Child, a própria subclasse onde o acesso ocorre.
Referência AccessRules: rejeitado
AccessCompilationTest.java
A única diferença relevante é o tipo declarado do parâmetro. Mesmo estando numa subclasse, não podemos invocar esse método protegido em qualquer objeto da classe base.
Cliente sem herança: rejeitado
AccessCompilationTest.java
Feche o quadro de protected: acesso de pacote funciona; subclasse externa exige as restrições vistas; cliente externo sem herança é rejeitado.
Limite à redução

A sobrescrita preserva o acesso

Um método público herdado continua público na sobrescrita.

Um método público de interface também exige implementação pública.

A regra evita que um subtipo retire uma operação disponível no contrato da base. Ela é um limite à recomendação de usar o menor acesso possível: a API herdada já impõe o mínimo.
Public para protected: não compila
AccessCompilationTest.java
O compilador rejeita uma sobrescrita que enfraquece o acesso. O diagnóstico específico distingue esse caso de um erro de sintaxe ou classe ausente.
Implementação de interface sem public: rejeitada
AccessCompilationTest.java
O método de Job é público implicitamente. A implementação de Worker sem modificador tem acesso de pacote e não satisfaz esse contrato. publicImplementation, no mesmo arquivo, testa a versão pública aceita.
04

Final não é imutável

Proteger a referência não protege automaticamente o objeto referenciado.

Proteger a referência não protege automaticamente o objeto referenciado.
Antes de executar

O cliente troca pdf por exe?

Um array público static final ainda permite alterar seus elementos.

Um getter que devolve o array interno produz o mesmo vazamento.

A lista de formatos é um exemplo de configuração exposta a consumidores. final impede reatribuir a referência; não impede substituir uma posição. Um array não vazio é mutável mesmo quando seus elementos são String.
As duas formas do vazamento
UnsafeFormats.java
A variável pública e o getter devolvem exatamente o mesmo armazenamento. Destacar que apenas trocar o campo para private, mantendo esse getter, não resolveria o problema.
O teste modifica a configuração global
FormatsTest.java
O teste restaura o elemento no finally para não contaminar os demais testes. A restauração é limpeza da demonstração, não uma solução do design.
Duas saídas: lista ou cópia
SafeFormats.java
List.of oferece lista não modificável com elementos String imutáveis. O array permanece privado e cada chamada devolve um clone. Escolha a forma de retorno conforme o uso do cliente; clones de arrays de objetos continuam rasos.
A cópia pode mudar; o original, não
FormatsTest.java
O teste modifica a cópia e consulta a API de novo. A diferença entre os dois resultados mostra que o estado interno permaneceu preservado.
A lista rejeita a modificação
FormatsTest.java
Uma constante pública pode ser adequada quando integra a abstração e contém valor primitivo ou objeto imutável. A garantia desta lista depende também de seus elementos serem imutáveis.
Uma distinção útil

Visão ou fotografia?

Visão não modificável

Não permite escrita pelo cliente, mas acompanha mudanças internas.

Cópia não modificável

Preserva os elementos observados na captura.

Esta extensão prática ajuda a escolher o contrato dos getters. Nem uma cópia de lista nem um wrapper torna objetos mutáveis contidos nela imutáveis. Aqui String permite separar o problema da estrutura do problema dos elementos.
A API explicita a semântica
FormatCatalog.java
view acompanha o catálogo; snapshot registra um estado. Ambos bloqueiam alteração da lista pelo consumidor. O catálogo em si é mutável e este exemplo não oferece sincronização.
O teste mostra o efeito da próxima alteração
FormatCatalogTest.java
As duas listas são obtidas antes de registrar epub. Só a visão passa a mostrar o novo formato. Não chame uma visão dinâmica de valor imutável.
05

Uma fronteira a mais: JPMS

Um tipo público pode pertencer a um pacote não exportado.

Um tipo público pode pertencer a um pacote não exportado.
Maven ≠ JPMS

Public não elimina exports

  • O módulo Maven organiza o build desta sessão.
  • module-info.java declara um módulo Java nomeado.
  • requires estabelece leitura; exports expõe um pacote.
  • Os testes usam dois módulos mínimos separados da aplicação Quarkus.
Atualize a perspectiva histórica da terceira edição: não repetimos uma recomendação geral de evitar módulos. Mostramos uma propriedade verificável no Java 25. exports regula acesso normal; opens trata reflexão profunda e não equivale a exports. Flags de override ficam fora desta demonstração.
A biblioteca exporta somente a API
module-info.java
O pacote club.tickets.internal não aparece na declaração. Seus tipos públicos continuam utilizáveis dentro do próprio módulo, mas não por um cliente externo via acesso Java normal no module path.
O teste aceita o cliente da API
ModuleBoundaryTest.java
As fixtures contêm o módulo club.client, que declara requires club.tickets e importa TicketOffice da API exportada. copySources copia as fixtures para o diretório temporário do teste e o compilador recebe module-source-path.
Public dentro de um pacote não exportado
SeatAllocator.java
A classe é public deliberadamente. A barreira que vamos verificar é a exportação do pacote, não o modificador da classe.
O teste rejeita a implementação interna
ModuleBoundaryTest.java
useInternalType troca o cliente para importar SeatAllocator. O erro package.not.visible confirma que o pacote não está disponível ao consumidor nomeado.
No classpath, sem descritores: acesso aceito
ModuleBoundaryTest.java
Este controle remove module-info.java e compila os mesmos tipos como código comum de classpath. Não estamos executando a aplicação Quarkus como um módulo JPMS, nem provando isolamento contra flags de abertura.
Aplicação em revisão de código

Antes de ampliar o acesso

  • Existe um consumidor legítimo para este membro?
  • Um teste no mesmo pacote seria suficiente?
  • O getter deixa escapar estado mutável?
  • Uma subclasse externa pode passar a depender deste detalhe?
  • Consigo mudar a representação sem mudar o contrato?
Reúna o que os testes mostraram: acesso mínimo protege invariantes e mantém opções de evolução. Serializable pode tornar parte do estado privado um compromisso de compatibilidade da forma serializada; isso é uma conexão com itens posteriores, não uma demonstração incluída aqui.
Exercício de dois minutos

Revise uma API real

Escolha um campo público, um helper público ou um getter de coleção de um projeto seu.

  1. Quem precisa acessá-lo?
  2. Que invariante pode ser violada?
  3. Qual é o menor contrato que atende o cliente?
Espere respostas antes de sugerir soluções. Volte a Inventory, TicketOffice e SafeFormats como três opções concretas. Se a API já foi publicada, reduzir acesso pode quebrar clientes; discuta migração em vez de aplicar uma mudança incompatível automaticamente.
