Protect the invariants

Before the code

Who can write −100?

An inventory starts with ten tickets. A reservation must be positive and cannot exceed availability.

A public field lets callers bypass that rule entirely.

Ask the audience to predict the next test. The problem is not merely an invalid value: the class loses control of all assignments made by clients. This demonstration is sequential; making the field private does not establish thread safety.
The failure: public representation
ExposedInventory.java
No domain operation stands between the caller and the state. Even constructor validation would not prevent the next assignment.
The test demonstrates the violation
InventoryTest.java
This test passes because it proves the broken example allows corruption. Green does not mean the design is good.
The fix: controlled operations
Inventory.java
State is private and reserve expresses the valid transition. Availability remains observable. The representation can change without changing the contract signature. This is not a concurrent implementation.
The test proves state preservation

The same instance receives three invalid attempts and still has ten tickets. Also show validReservation during the live demonstration to cover the successful path.

Implementation

SeatFormatter: package access.
Ticket: private nested class.

An ordinary top-level class can be public or package-private; private and protected apply to members, including nested types. If a helper serves just one class, consider a private static nested type. Internal names do not appear in the public return type.
One facade, one private type
TicketOffice.java
Point to issue and the Ticket class. The private implementation owns its fields and validation, while clients receive a String. Private access is allowed within the enclosing top-level type and its nested types.
The test uses only the contract

The package is also a boundary
SeatFormatter.java
This helper deliberately demonstrates package access. Since only the facade uses it today, it could also be nested. The example keeps both alternatives visible for discussion.
Same-package testing, no extra API
TicketOfficeTest.java
The helper does not need to be public to be tested. The src/test location does not change the rule: the package declaration determines access.

03

Choose the narrowest necessary access

Start with private. Widen only to serve a legitimate consumer.

Start with private. Widen only to serve a legitimate consumer.
Class members

Four levels, different commitments

  • private · within the top-level type and its nested types
  • No modifier · same package
  • protected · same package + subclasses, with restrictions
  • public · clients with access to the type and package
Accessibility also depends on the enclosing type and, for named modules, module readability and package exports. Protected does not mean subclasses only: unrelated same-package classes also have access. The next tests check these cases.
Four methods to experiment with
AccessRules.java
This class exists only to demonstrate language rules. It is not a recommendation to create four equivalent production API operations.
Same package: protected works too
AccessRulesTest.java
The test class is not an AccessRules subclass. It can still access packageCode and protectedCode because it belongs to the same package.
Private stays private within a package
AccessCompilationTest.java
Client declares the same package but is a separate top-level type. privateCode remains inaccessible. Contrast this with package access on the previous slide.
Subpackages do not inherit package access
AccessCompilationTest.java
Dots in package names organize names; they do not create parent-child access privileges. access.client is a different package from access.
Protected outside the package

The receiver type also matters

An external subclass can access the instance member through this or a receiver of its own type, or a subtype.

A receiver typed as the superclass does not get that permission.

This restriction concerns protected instance members outside the package, not every protected member. Access must occur in the subclass body. On a public exported type, protected is also an API commitment to external subclasses.
Child receiver: accepted
AccessCompilationTest.java
Ask for a prediction before pointing to successful true. The receiver other has type Child, the subclass where access occurs.
AccessRules receiver: rejected
AccessCompilationTest.java
The relevant change is the declared parameter type. Even inside a subclass, we cannot invoke this protected method on an arbitrary base-class receiver.
Unrelated client: rejected
AccessCompilationTest.java
Complete the protected picture: same-package access works; an external subclass must satisfy the restrictions just shown; an unrelated external client is rejected.
A limit to narrowing

An override preserves access

An inherited public method remains public when overridden.

A public interface method also requires a public implementation.

The rule prevents a subtype from removing an operation available in the base contract. It limits the least-access recommendation: the inherited API already sets the minimum.
Public to protected: does not compile
AccessCompilationTest.java
The compiler rejects an override that weakens access. The specific diagnostic distinguishes it from syntax errors or missing classes.
Interface implementation without public: rejected
AccessCompilationTest.java
Job.run is implicitly public. Worker.run without a modifier has package access and cannot satisfy the contract. publicImplementation in the same file tests the accepted public version.
04

Final does not mean immutable

Protecting a reference does not automatically protect the referenced object.

Protecting a reference does not automatically protect the referenced object.
Before running

Can a client replace pdf with exe?

A public static final array still allows changes to its elements.

A getter returning the internal array causes the same leak.

The format list represents configuration exposed to consumers. Final prevents reference reassignment; it does not prevent replacing an element. A non-empty array is mutable even when its elements are Strings.
Two forms of the leak
UnsafeFormats.java
The public variable and the getter expose the exact same storage. Making only the field private while retaining this getter would not solve the problem.
The test changes global configuration
FormatsTest.java
The test restores the element in finally to avoid contaminating other tests. Restoration is demonstration cleanup, not a design fix.
Two solutions: a list or a copy
SafeFormats.java
List.of supplies an unmodifiable list with immutable String elements. The array stays private and each call returns a clone. Choose the return type to suit the client; object-array clones remain shallow.
The copy can change; the original cannot
FormatsTest.java
The test mutates the copy and queries the API again. The different results demonstrate that internal state was preserved.
The list rejects modification
FormatsTest.java
A public constant can be appropriate when it belongs to the abstraction and holds a primitive or immutable object. This list guarantee also depends on its elements being immutable.
A useful distinction

A view or a snapshot?

Unmodifiable view

Prevents client writes but observes internal changes.

Unmodifiable copy

Preserves the elements observed at capture time.

This practical extension helps choose getter contracts. Neither a list copy nor a wrapper makes mutable elements immutable. Strings let us separate collection structure from element mutability.
The API makes the semantics explicit
FormatCatalog.java
View tracks the catalog; snapshot captures a state. Both prevent callers from changing the returned list. The catalog itself is mutable and this example does not provide synchronization.
The test shows what the next change does
FormatCatalogTest.java
Both lists are obtained before registering epub. Only the view shows the new format afterward. Do not describe a dynamic view as an immutable value.
05

One more boundary: JPMS

A public type can belong to a non-exported package.

A public type can belong to a non-exported package.
Maven ≠ JPMS

Public does not bypass exports

  • The Maven module organizes this session build.
  • module-info.java declares a named Java module.
  • requires establishes readability; exports exposes a package.
  • Tests use two minimal modules separate from the Quarkus application.
Update the third edition historical perspective: we do not repeat a blanket recommendation to avoid modules. We demonstrate a verifiable Java 25 property. Exports governs ordinary access; opens concerns deep reflection and is not equivalent to exports. Override flags are outside this demonstration.
The library exports only its API
module-info.java
The declaration does not list club.tickets.internal. Its public types remain usable within the module, but not through ordinary Java access by an external module-path client.
The test accepts the API client
ModuleBoundaryTest.java
Fixtures include club.client, declaring requires club.tickets and importing TicketOffice from the exported API. CopySources copies the fixtures into the test temporary directory and the compiler receives module-source-path.
Public inside a non-exported package
SeatAllocator.java
The class is deliberately public. The boundary under test is package export, not the class modifier.
The test rejects the internal implementation
ModuleBoundaryTest.java
UseInternalType changes the client to import SeatAllocator. The package.not.visible error confirms the package is unavailable to the named consumer.
On the classpath, without descriptors: access accepted
ModuleBoundaryTest.java
This control removes module-info.java and compiles the same types as ordinary classpath code. We are not running Quarkus as a JPMS module or claiming isolation against opening flags.
Applying this in code review

Before widening access

  • Does this member have a legitimate consumer?
  • Would a same-package test be sufficient?
  • Does the getter leak mutable state?
  • Could an external subclass depend on this detail?
  • Can the representation change without changing the contract?
Bring together what the tests showed: minimal access protects invariants and preserves evolution options. Serializable can turn private state into a serialized-form compatibility commitment; this connects to later items and is not demonstrated here.
Two-minute exercise

Review a real API

Choose a public field, public helper, or collection getter from one of your projects.

  1. Who needs access?
  2. Which invariant could be violated?
  3. What is the smallest contract that serves the client?
Wait for answers before suggesting fixes. Revisit Inventory, TicketOffice, and SafeFormats as three concrete options. If an API is already published, narrowing access can break clients; discuss migration rather than automatically applying a breaking change.
